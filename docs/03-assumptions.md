# 03 · 假设登记表（H1–H10）

> **唯一事实源是代码**：`server/domain/assumptions.mjs` 的 `ASSUMPTIONS` 常量（接口 `GET /api/assumptions`，
> 前端 `#/assumptions` 页）。本文件是它的说明版，两者不一致时以代码为准。
> 这些假设来自 v1 证据链审计（`E:\Claude_PRD\notes\evidence-audit.md` §6.2）——它们是「产品事实」与「工程推断」之间
> 的缝隙。**依赖某条假设的结论，必须在该结论里挂上对应编号。**

| id | 假设 | 置信度 | 若被推翻的影响 | 如何证伪（probe） |
|---|---|---|---|---|
| **H1** | 建议数量 = `ceil(公式值)` 向上取整 | 中 | 取整方向决定"多订 1 件 vs 少订 1 件"；若为 round，部分 SKU 会少订 | 用库存与近 15 天销量已知的商品，在真实后台生成建议，反算取整方向 |
| **H2** | 统计窗口 = 近 15 个**自然日**（含零销量日，缺日补 0） | 中高 | 若实为 16 个点（闭区间 off-by-one），日均偏差 ~6.7%，建议量同比例偏移 | 取两款 SKU，用已知 15/16 天出库量反算后台日均 |
| **H3** | 综合系数窗口 = `[到货日, 到货日+周期−1]`（闭区间） | 中 | 多算/少算一天 → 系数偏离 1/周期 权重；节假日靠窗时影响放大 | 设周期 5 天、把某天双休日系数设 2，看系数是 1.2 还是 1.1667 |
| **H4** | 低库存预警 = `实物库存 + 在途库存 < 下限` | **中（高风险）** | 换成「实时库存 < 下限」会改变全量 SKU 是否产出建议（在途大的商品尤其敏感） | 构造"实物 0 + 在途 100、下限 10"的商品，看后台是否显示低预警 |
| **H5** | 动态上下限 = `ceil(可售天数 × 日均销量)` | 低 | 上下限差 1 件可能导致某 SKU 进/出建议 | 设可售天数 7、日均 0.067，看后台下限显示 0 还是 1 |
| **H6** | 方案 2 的「当前实物库存」= 实物（不减占用/在途） | 中 | 高占用商品的建议量会偏大 | 取高占用商品，看建议 = 上限−实物 还是 上限−可售 |
| **H7** | 日均销量含零销量日、不冲减退货 | 中 | 若后台只按"有销量日"求均值，低频商品日均会被显著高估 | 取 15 天内仅 3 天有销量的 SKU，反算分母是 15 还是 3 |
| **H8** | 建议数量 ≤0 不展示该行 | 低 | 若线上展示 0/负行，本实现会"少显示"部分商品 | 构造库存充足商品，看建议列表是否出现该行 |
| **H9** | 补货建议**没有**开放平台接口，只能 UI/RPA 或自建 | 高 | 若存在未公开接口，集成路径可缩短 | 有赞云控制台按 `replenish/suggest/备货` 关键词检索（v1 已核 81 接口 + 56 消息零命中） |
| **H10** | σ 方案（服务水平法）是本实现增强，不是有赞行为 | 高 | 无（只要不标 documented） | 无需验证；保持 `provenance='enhancement'` |

## 使用纪律

1. **代码里只写编号，不写散落文案**：`assumptions: ['H1','H2','H4']`。
2. **前端必须可点开**：结论旁的橙色徽标 → `#/assumptions` 对应条目 → 显示 `statement / confidence / risk / probe`。
3. **工具描述里要带假设**：模型看到 `suggestion.compute` 的描述时，就知道"这个数字依赖 H1/H2/H4"，
   从而在回答用户时主动提示不确定性（这是 v2 相对 v1 的关键差异：**不确定性随数字一起流动**）。
4. **假设不阻塞交付，但阻塞"声称"**：可以按 H1 实现，但不能说"这就是有赞的行为"。
